# Removing a Tenant is disabling it; destroying it is a second, deliberate step

`DELETE /admin/tenants/{slug}` switches a Tenant off rather than destroying it: `tenants.disabled_at` is stamped, the Tenant stops resolving from any hostname, and every public surface it had — Self-Service Flows, the OAuth2 endpoints, JWKS, discovery — stops answering. `POST /admin/tenants/{slug}/enable` switches it back on. Nothing the Tenant owns is deleted, and its slug remains taken. `DELETE /admin/tenants/{slug}?purge=true` is the irreversible one: it destroys the Tenant and everything it owns and frees the slug, and is refused unless the Tenant is already disabled. This exists because a Tenant could previously be created but never removed: a provisioning saga that compensates left an orphaned Tenant behind forever, and test and dev instances accreted dead Tenants with no remedy short of dropping the database ([#8](https://github.com/katipwork/pratu/issues/8)).

Decisions that were open questions, settled here:

- **The unqualified `DELETE` is the soft one, because the blast radius of the alternative is a customer's entire identity namespace.** A Tenant owns every Identity, credential, Session and OAuth2 client under it. A hard delete cascading through all of that is unrecoverable, and it is the operation most likely to be issued by a script with the wrong slug in a variable. So the destructive reading is never the default one: the bare verb disables, and destruction has to be asked for by name.

- **A purge is reachable only from the disabled state.** `?purge=true` on a live Tenant is a `409` naming the missing step, not a destruction. Two steps make the dangerous act deliberate without making it hard: each is idempotent, so a compensating saga just issues both. A wrong slug in a script therefore costs a disable — undone with one call — instead of a customer's identities, because the wrong slug is overwhelmingly likely to name a *live* Tenant.

- **An unparseable `purge` is a `400`, never a guess.** Silently disabling for a caller who typed `?purge=yes` would report success for work that did not happen, and they would believe the data was gone.

- **Disabling holds the slug; only a purge frees it.** A slug is a DNS label: `{slug}.{base_domain}` is the Tenant's address (ADR 0003). If disabling freed the slug, a later Tenant could take it and that address would quietly come to mean a *different* isolated identity namespace — with every stale bookmark, cached OAuth2 client config and resource server still pointing at it. Silently changing what an address means is precisely the multi-tenant failure worth engineering against, so re-using a slug is exactly as deliberate as destroying the data behind it: the same act, in one place. A saga that compensates and then retries the same slug either re-enables the Tenant or purges it first; re-creating over a merely-disabled slug is `409`.

- **The public surface stops; the admin surface does not.** Disabled Tenants are invisible to hostname resolution and fully visible to the admin API — listable, readable, patchable, and re-enablable. An operator who cannot see what they just switched off cannot undo it. The seam is the store: `FindBySlug`/`FindByDomain` (the `tenant.Store` the Resolver holds) filter disabled Tenants out, so the public path cannot serve one even if a future handler forgets to check, while the admin API asks for them explicitly through `FindBySlugIncludingDisabled`.

- **Disabling is idempotent; a Tenant that was never there is 404.** Compensation runs more than once. Disabling an already-disabled Tenant answers exactly as the first call did — and `disabled_at` keeps its original value, so the timestamp means "when it went off", not "when someone last asked". An absent slug is a 404, matching every other admin sub-resource.

- **Sessions are not revoked, and tokens are not blacklisted.** Neither is needed for the Tenant to stop working: every request resolves the Tenant by hostname first, so a Session cookie or session token for a disabled Tenant is inert. Leaving them intact is what makes re-enabling restore the Tenant whole instead of signing everyone out.

## Consequences

- CONTEXT.md's Tenant entry names the disabled state and the word for it — _disabled_, not _deleted_ (nothing is destroyed), _suspended_ (which reads as billing) or _archived_ (which reads as read-only). Destroying one is _purged_.
- Every tenant-owned table reaches `tenants(id)` by a foreign key with `ON DELETE CASCADE`, and referential actions bypass RLS, so a purge sweeps them without a tenant context. `rate_limits` is the exception — platform-level, no foreign key, keyed by strings that embed the tenant id — so a purge deletes its rows explicitly; leaving them would leave the purged Tenant's identifiers behind. A new tenant-owned table that follows the ADR 0004 rule is swept automatically; one keyed like `rate_limits` must be added to the purge by hand.
- An already-issued access token stays cryptographically valid until it expires (15 minutes). A resource server that re-fetches JWKS fails immediately, because the Tenant's `.well-known` endpoint no longer resolves; one holding a cached JWKS honours the token until expiry. Disabling is not a revocation primitive.
- Courier messages already queued when a Tenant is disabled still drain, since the outbox is drained platform-wide and the Tenant can no longer enqueue new ones. A disabled Tenant can therefore still deliver an in-flight One-Time Code.
- `POST /admin/tenants` still refuses a slug held by a disabled Tenant with `409 slug already in use`; the error says so, so a caller can tell "taken by a live Tenant" from "held by one I disabled".
- Disabling alone leaves orphans accumulating as rows; a compensating saga that wants the storage and the slug back issues the disable and then the purge.
